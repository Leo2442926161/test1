## 1. 运行形态

同一套节点逻辑今天只在 Linux 宿主上链接。目标形态是把 `fw_node.c`、`fw_ux.c`、`fw_status.c` 编进 nRF54L15 应用；`fw_sim.c` 留在宿主。`firmware/nrf/` 有 NCS 空壳（`west.yml`、`prj.conf`、无脚号的 overlay），**没有**把上述 C 文件编进去，也没有分区表或烧录文件。`firmware/build/fw_sim` 是这一次宿主编译的进程，MANIFEST 里对它的说明是 host build, not an nRF image。

三层职责与 ICD 一致，落地程度不同：

| 层 | 产品含义 | 宿主现状 |
|---|---|---|
| L0 | 本地烟/CO 判决后本机蜂鸣 + 灯。ICD 预算：判决到声光 ≤50 ms，报警先开 `LED_RGB_EN` 再出灯帧 | `fw_set_alarm` 在同一次调用里置 `horn_on` 并 `fw_ux_set`。没有周期精确的 50 ms 测量，也没有像素帧缓冲 |
| L1 | 同品牌、同组、离线无线跟报。Matter 与云不参与这条路径 | 内存计数 `alarm_relay_tx/rx`。`fw_sim hop` 在两个 `fw_node_t` 之间递一帧。没有 Thread 射频 |
| L2 | Matter 只做状态/事件通知 | `matter_notify_attempts` / `matter_notify_sent` 与 `matter_role=notify_only`。没有 Matter 协议栈 |

```text
CLI / 未来传感驱动
        │  fw_set_alarm / fw_mute / fw_tick
        ▼
   fw_node.c          hush、角色、级联 TX 计数、Matter 通知计数
        │  fw_ux_set / fw_ux_tick
        ▼
   fw_ux.c            SED 钳位、LED_RGB_EN、估算电流
        │
        ▼
   fw_status.c        一行 JSON（钩子回读）
```

宿主进程 `fw_sim` 持有节点 A（DUT）和节点 B（peer）。`--state` 文件是命令回放日志，不是片上 NVS。

## 2. 模块

### 2.1 节点与 Hush — `src/fw_node.c`

公开版本串是 `FW_VERSION` = `fw-hush-relay-0.1.0-evt`，ICD 基线串是 `v0.1.7`。

`fw_node_init` 的上电默认：

| 字段 | 初值 | 说明 |
|---|---|---|
| `relay_enable` | true | 注释写明对应 NVS 默认开。今天就是结构体里的布尔，不是 Zephyr settings |
| `hush_cfg_s` | 540 | 等于 `HUSH_SMOKE_S`。可改范围 480–600，改的是节点配置，不改宏 |
| `sensing_active` | true | 消音期间仍为 true |
| `voice_enable` | true | 只存储。声光限额不读它 |
| `ux.mode` | idle | `led_rgb_en=false`，`led_status_on=true`，`led_status_avg_ua=500`（0.5 mA 模型） |

烟消音窗 `MuteWindow`：

| 规则 | 实现 |
|---|---|
| 只挂烟报警 | `fw_mute`：`alarm==SMOKE` 才进入。置 `hush_active`，`hush_remaining_s=hush_cfg_s`，`horn_on=false`，`full_alarm_light=false`，光效 `FW_UX_MUTE_HOLD` |
| CO 拒绝 | `alarm==CO` 时返回 -1，`hush_reject=co_forbidden`（JSON 字符串 `co_forbidden`）。蜂鸣与报警灯保持原状 |
| 无报警 | 返回 -1，`hush_reject=no_alarm` |
| 时长 | 默认 540 s。`fw_set_hush_smoke_s` 只接受 480–600。越界返回 -1 且不改当前配置 |
| 虚拟时间恢复 | `fw_tick(dt)` 扣 `hush_remaining_s`。减到 0 且烟条件仍在：重新 `horn_on`、`full_alarm_light`，光效回到 `FW_UX_PULSE_SMOKE`。套件禁止用墙钟等待；`tick 540` 是 9 分钟 |
| 危急打断 | `fw_critical`：清消音窗，恢复完整声光。无报警时返回 -1 |
| CO 出现打断烟消音 | `fw_set_alarm(CO)` 或对端注入 CO 且本机正在 hush：立即清 `hush_active` |
| 不压他机 | `fw_mute` 不增加 `alarm_relay_tx`，帧里没有「把对方消音」位。`silenced_by_remote_hush` 在现有路径上保持 false |
| 声光不可被用户永久关闭 | `fw_user_disable_horn` 恒返回 -1 |

确认窗 20 s 与 MuteWindow 是两件事。本包没有确认窗状态。

### 2.2 级联 — 仍在 `src/fw_node.c`，递交在 `fw_sim.c`

本地报警后的发送 `relay_on_local_alarm`：

1. `alarm==NONE` 则返回。
2. `relay_enable==false` 或 `group_id==0`：不发送。L0 声光已经在前面写好。
3. `tx_fail==true`：`cascade_fail_count++`，不增加 `alarm_relay_tx`。蜂鸣保持。
4. 否则：`alarm_relay_tx++`，`tx_seq++`，`last_tx_type=alarm`。

接收 `fw_alarm_relay_inject_rx(dst, type, src_group)`：

| 条件 | 结果 |
|---|---|
| type 不是烟或 CO | 返回 0，丢弃 |
| 目的 `relay_enable==false` | 返回 0 |
| 任一侧 `group_id==0` 或两组不同 | 返回 0 |
| 通过 | 返回 1。`alarm_relay_rx++`，`role=follow`，同类型本地声光。不拷贝源端 hush |

`fw_sim` 的 `hop` 只在 DUT 的 `tx_seq` 比 peer 已应用序号新时，把 `last_tx_type` 与 DUT 组号注入 peer。`pair` 把两侧 `group_id` 设为 1。`cloud 0|1` 只改 `cloud_up`，不参与是否发送。

`fw_clear_alarm` 把本机报警、消音、蜂鸣和角色清回 idle，并 `fw_ux_set(IDLE)`。它不发出「解除跟报」帧。对端如果已经 follow，不会被这次 clear 自动关掉。解除帧列为待补（见缺口清单）。

### 2.3 SED 与光效 — `src/fw_ux.c`

ICD 的 `ux_light_set` / `ux_light_get_status` 在 C 里是 `fw_ux_set` / `fw_ux`。CLI 是 `ux MODE WINDOW BRIGHTNESS SEGMENTS FLAGS` 与 `status`。负的 window / brightness / segments 表示用该模式默认值。

已进入枚举的模式：

| 枚举 | CLI 名 | 默认窗 / 亮度% / 段数 | 上限 | `LED_RGB_EN` |
|---|---|---|---|---|
| `FW_UX_IDLE` | `idle` | 0 / 0 / 0 | — | 0。状态点模型 500 µA |
| `FW_UX_RING_SWEEP` | `ring_sweep` | 8 / 25 / 8 | 窗≤8，亮度≤25，段数≤窗 | 1。周期 1200 ms |
| `FW_UX_PATH_GUIDE` | `path_guide` | 与环扫相同的默认和上限 | 同左 | 1。代码没有单独的路径灯通道 |
| `FW_UX_PULSE_SMOKE` | `pulse_smoke` | 0 / 70 / 16 | 段≤16，红橙亮度≤70 | 1 |
| `FW_UX_PULSE_CO` | `pulse_co` | 同烟脉动的限额 | 同左 | 1 |
| `FW_UX_PULSE_FAULT` | `pulse_fault` | 走 P0 脉动分支（`is_p0_pulse` 含 fault） | 段≤16，亮度≤70 | 1 |
| `FW_UX_MUTE_HOLD` | `mute_hold` | 6 / 20 / 4 | 窗≤8，亮度≤25 | 1 |
| `FW_UX_FULL_WHITE` | `full_white` | 64 / 100 / 64 | 仅 `flags` 含 `factory` | 工装路径置 `external_power` |

限额动作与 ICD 钩子对齐：

| 测项 | `limit_action` | 行为 |
|---|---|---|
| L1 窗>8 | `clamp` | 非 P0 把 window 钳到 8 |
| L2 亮度>25% | `clamp` | 非 P0 亮度钳到 25 |
| L3 环扫超过 60 s | `stop` | `fw_ux_tick` 在 `RING_SWEEP` 上累计。超过 `FW_L3_SWEEP_MAX_S`（60）后回 idle，`LED_RGB_EN=0`，`cooldown_remain_s=300`。冷却期内再请求环扫：`reject` / `cooldown` |
| L4 idle | 强制 EN=0 | 进入 idle 的分支写 `led_rgb_en=false` |
| L5 报警超段/超亮 | `clamp` | P0 段数钳 16、亮度钳 70。`horn_on` 由节点逻辑保留 |
| L6 满幅白 | `reject` / `full_white` | 无 `factory` 标志时 `fw_ux_set` 返回 -1，不进入该模式 |
| L7 射频高峰 | `clamp`，`rf_half=true` | 标志 `FW_UX_FLAG_RF_PEAK`（CLI `rf`）。非 P0 亮度再钳到 **12**。规格文字是 ≤12.5%，`uint8` 百分比存不下 0.5。窗不减半 |
| L8 语音 | 无单独光效分支 | `voice_enable` 不改变段数和亮度。`fw_user_disable_horn` 拒绝关声 |
| L9 级联 | 峰值模型含 TX 预算 | `relay_enable=0` 不发 TX；`tx_fail` 不挡本机声光；估算电流仍须 ≤600 mA |
| 峰值墙 | `clamp` / `peak` | 见下。短脉冲墙 1200 mA 只作为常量出现在 JSON，宿主不采样分流器 |

估算电流（设计假设，写在 `fw_ux.c` 文件头，不是钳表）：

```text
led_mA = segments * 45 * brightness / 100
total  = led_mA + (horn ? 120 : 0) + (cascade_tx_budget ? 40 : 0)
```

`cascade_tx_budget` 在 `relay_enable && !tx_fail && group_id!=0 && alarm!=NONE` 时为真。超过 `FW_PEAK_CONTINUOUS_MA`（600）时先降亮度（不低于 10）再减段数（不低于 1），并打上 `reject_reason=peak`。工装满幅白不把 TX 预算算进去，并标记 `external_power`。

`fw_ux_push_frame`：`led_rgb_en==false` 时返回 -1，否则返回 0。函数不产出 64 段 RGB 帧，也不操作 P2.06/P2.07/P2.08。这些脚在 ICD 网表草案里，驱动待补。

### 2.4 Matter 通知 — `fw_node.c` 内的计数，不是协议栈

`note_matter` 在 `fw_set_alarm` 末路调用：`matter_notify_attempts++`；仅当 `matter_session==true` 时 `matter_notify_sent++`。会话断开时尝试数增加、成功数不增加，同时 L0 蜂鸣与 L1 `alarm_relay_tx` 照常。

固定策略（函数返回值，测试直接断言）：

| API | 值 |
|---|---|
| `fw_matter_role` | `"notify_only"` |
| `fw_matter_equals_cascade` | false |
| `fw_wired_interconnect_supported` | false |

`firmware/policy/claims.txt` 与之锁在同一包里，供 `TC-MATTER-BOUND-02` 与 `TC-CLAIM-BOUND-01` 读取：

```text
matter_role=notify_only
matter_equals_cascade=false
wired_interconnect=false
ac_interconnect_wire_claim=false
ul_en_wired_multiple_station_claim=false
allowed_wording=同品牌无线跟报
allowed_wording=Matter 状态/事件通知
```

Listing / 说明书抽检不在 `make test` 里。那两项用例的通过打印写明 package policy lock; listing pack is manual。

通知失败不得回退 `horn_on`，也不得用 Matter 计数代替 `alarm_relay_tx`。现有代码没有「通知失败则改蜂鸣」的分支。

### 2.5 状态 JSON — `src/fw_status.c`

`fw_status_json(dut, peer, buf, len)` 打一个对象。`peer==NULL` 时 `"peer": null`。DUT 带 `ux` 对象；peer 只有 hush/级联字段，不带 ux。

顶层还有：`version`、`icd_baseline`、`image`（固定 `"host-sim"`）、`mcu_target`（`"nRF54L15"`）、`ncs_board_build`（false）、`HUSH_SMOKE_S`、`hush_cfg_s`、`cloud_up`、`matter_session`、`matter_role`、`matter_equals_cascade`、`wired_interconnect`、`matter_notify_attempts`、`matter_notify_sent`、`cascade_fail_count`、`voice_enable`、`peak_continuous_limit_ma`（600）、`peak_pulse_limit_ma`（1200）、`l7_brightness_ceiling_pct`（12）。

CLI 在领域拒绝（CO 消音、满幅白、冷却期）时仍打印 JSON 且进程退出码 0。命令写错才是非 0。

## 3. 钩子表

G3 与 Issue #15 要回读的名字。宿主上 JSON 与 C 都能读到。样机 UART/RTT 尚未接。

| 钩子 | JSON | C |
|---|---|---|
| 消音是否有效 | `hush_active` | `fw_hush_active` |
| 剩余秒 | `hush_remaining_s`，别名同值 `hush_remain_s` | `fw_hush_remaining_s` |
| 拒绝原因 | `hush_reject`，别名 `hush_reject_reason`：`none` / `co_forbidden` / `no_alarm` | `fw_hush_reject` |
| 级联发送 / 接收 | `alarm_relay_tx` / `alarm_relay_rx` | `fw_alarm_relay_tx` / `fw_alarm_relay_rx` |
| 级联开关 | `relay_enable` | `fw_relay_enable` / `fw_nvs_set_relay_enable` |
| 默认窗常量 | `HUSH_SMOKE_S` = 540 | 宏 `HUSH_SMOKE_S` |
| 灯限额 | `ux.applied_window` `applied_brightness` `applied_segments` `led_rgb_en` `limit_action` `reject_reason` `rf_half` `sweep_elapsed_s` `cooldown_remain_s` | `fw_ux()` 指向 `fw_ux_t` |

`limit_action` 字符串：`none` / `clamp` / `reject` / `stop`。  
`reject_reason` 字符串：`none` / `window` / `brightness` / `cooldown` / `full_white` / `peak` / `other`。  
窗口钳位在实现里体现在 `applied_window` 与 `limit_action=clamp`，没有单独把 `reject_reason` 设成 `window` 或 `brightness` 的分支；那两个枚举值存在，供回读约定，当前钳位路径用 `none` 或随后被峰值逻辑写成 `peak`。

附加回读（验收最小集之外，但 JSON 已有）：`horn_on`、`alarm_light_on`、`cascade_role`（`idle`/`origin`/`follow`）、`silenced_by_remote_hush`、`alarm_relay_tx_type`、`alarm_relay_rx_type`、`est_continuous_ma`、`led_status_avg_ua`。

## 4. OTA 与 Matter 的边界

Matter 在本包的全部代码量是：一个会话布尔、两个计数、三个恒定策略函数、`policy/claims.txt` 里的七行。没有配网、集群、订阅、证书或控制器。

OTA 在本包中没有实现：

| 边界 | 现状 |
|---|---|
| 镜像传输、版本比较、A/B 槽、MCUboot | 无源文件 |
| ICD 探针里的「OTA 拒升」 | 无函数。不能从本包演示拒升 |
| 射频高峰把非 P0 亮度减半 | 只有测试注入的 `FW_UX_FLAG_RF_PEAK`。没有射频栈回调去置这个标志 |
| 用 Matter 或 OTA 代替 L0/L1 | 策略函数与测试禁止。`matter_equals_cascade=false` |

手机 App 同样没有工程。通知计数不能当作 App 已能显示报警。

## 6. 上 nRF54L15 时要守的契约（未实现）

下面是 `firmware/README.md` 已经写给移植的接口。NCS 空壳在 `firmware/nrf/`（见该目录 README）；`ncs_board_build` 仍为 false。完成标准在 Issue #15：可烧录镜像 + 哈希、样机能回读本节第 3 节的钩子、测试对实机 P0 与 PWR 出通过或退回单。

1. 把 `include/fw.h` 与 `src/fw_node.c`、`fw_ux.c`、`fw_status.c` 编进 NCS 应用。`fw_sim.c` 不进镜像。
2. `BTN_TEST_MUTE` 短按调用 `fw_mute`。烟/CO 判决调用 `fw_set_alarm`。1 Hz 调用 `fw_tick(1)`。光学与 CO 驱动本身待补，判决入口先接这条 API。
3. `relay_enable` 改存 Zephyr settings，默认开。
4. 级联帧只带报警类型和组号。不带远程消音位。`fw_mute` 不发这种帧。
5. Matter 沿用通知计数的语义：失败不回退 `horn_on`，不代替 `alarm_relay_tx`。协议栈待补。
6. 产测把 `fw_status_json` 打到 UART 或 RTT，字段名与 CLI 相同。
7. 在板级构建出现之前，不把 `build/fw_sim` 写入芯片，也不把宿主 SHA 填进「镜像哈希」一栏。

ICD 草案脚（实现时由硬件网表最终确认，软件这里不另编一套）：`LED_STATUS` P0.01，`LED_RGB_DATA` P2.06，`LED_RGB_CLK` P2.07（单线时 DNP），`LED_RGB_EN` P2.08 且 idle 为 0。`HORN_DRV` 不与唤醒脚复用。这些 GPIO 操作在宿主模型里不存在。这些编号也没有写入 `firmware/nrf/` 的 overlay；待确认项在 `firmware/nrf/HARDWARE_NEEDED.md`。

## 7. 与 FSM v0.3 的差异（宿主子集）

FSM 草案里的下列项没有对应实现，详细设计不把它们算进 `fw-hush-relay-0.1.0-evt` 的功能表：

| FSM / 产品项 | 宿主 |
|---|---|
| `Spin_Short`、`ClearSweep` | 枚举中无 |
| 64 段 chase 的像素时序、1.0–1.5 s 真正换帧 | 只保存 `sweep_period_ms=1200` 与段数计数 |
| 烟红 `#FF1A1A`、CO 橙 `#FF7A00` 的色点缓冲 | 模式名区分烟/CO，无 RGB 帧 |
| 语音短句播放 | `voice_enable` 布尔。文案在语音短句 v0.1.1，无音频资源 |
| 低电啁啾、仓盖、光学双轨、CO 偏置 | 无驱动、无状态 |
| 有线 `INTERCONNECT` | 策略与 API 均为 false。网表侧也不设这条默认轨 |

已对齐并有宿主测试的，是第 2 节的 Hush、同组离线跟报、SED 钳位和 Matter 通知边界。
